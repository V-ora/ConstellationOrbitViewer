# 制作记录 07 · 卫星百科访问路径与"换网后要做什么"（2026-11-09）

## 一、结论先行

| 环境 | 能否访问卫星百科 | 说明 |
|---|---|---|
| 本机（家宽） | **能，但有限流** | 今天连续测试后被 403 封了一段，需要冷却 |
| GitHub Actions runner（Azure 机房 IP） | **不能** | 自检 `cache/wiki_status.json` 记录：两条词条都 403（0 字节） |

所以**不要把"卫星百科同步"当成 CI 的可靠数据源**：CI 那一步永远是 `continue-on-error`，
拿不到就沿用现有任务表。真正的更新时机是**在本机运行一次**。

## 二、稳定访问的三个要点（实测得出）

1. **必须带浏览器头**
   `UA: Mozilla/5.0 …Chrome/124` + `Accept: application/json` + `Accept-Language: zh-CN`
   —— 只给 `UA: ConstellationOrbitViewer` 会被 Cloudflare 反爬页拦（403 +「请稍候…」）。
2. **先热身拿 cookie**
   `GET https://sat.huijiwiki.com/` 即使回 403，也会下发 `__cf_bm`；
   带着这个 cookie 再调 `api.php` 就是 200（实测 102 KB）。
   代码里是 `_wiki_opener()`（带 CookieJar，缓存 30 分钟）。
3. **限速 + 手别欠**
   页间至少 12 秒（`_wiki_gap(12)`）；**403 后不要重试**，直接休息 10 分钟
   （`_WIKI_BLOCKED`），否则封禁时间会越拉越长——今天就是我反复测把它惹毛的。

## 四、顺便记一笔：git 为什么一直失败

全局配置里有：

```
http.https://github.com.proxy = http://127.0.0.1:7892
```

而 7892（Clash 混合口）当时没监听 —— 于是 `clone/fetch/push` 全部
`Failed to connect ... over proxy 127.0.0.1`。这也解释了之前为什么每次推送都要绕
GitHub API 手工建 blob/tree/commit。

已执行：`git config --global --unset http.https://github.com.proxy`
→ 直连 `git push` 正常（2026-11-09 验证，`16b22c8`）。
若以后又要走代理，重新设置这个 key 即可。

## 五、web_live 的定位（顺手统一）

`web_live/raise/` 是 exe 运行时的**磁盘覆盖层**（改了页面不用重打包也能生效）。
它属于运行期副本，**不入库**（`.gitignore` 已排除）；由 `sync_web_live.py` 从
`web/raise/` 镜像生成，`build_pages.py` 开头会自动跑一次。
之前我用 API 把它推进了仓库，造成本地/远端不一致，已 `git rm --cached` 清理。

## 六、让网站脱离本机自主更新（2026-11-09 补充）

结论：**卫星百科不是唯一来源**。在 CI runner 上实测四个源：

| 源 | runner 可达 | 说明 |
|---|---|---|
| sat.huijiwiki.com | ✗ 403 | 恒封，本机偶尔能通 |
| zh.wikipedia.org | ✓ 200 | 可用于查条目，但解析成本高 |
| **planet4589.org (GCAT)** | ✓ 200 / 13.8 MB / **0.9 秒** | **Launch_Tag 就是 COSPAR**，直接可用 |
| r.jina.ai | ✓ 200 但仅 505 B | 拿不到正文，放弃 |

GCAT 的 launch/launch.tsv 能直接给出：

`
2026-248 → Lijian-2  Y2   JQ/LC140    2026 Nov 3 00:15 UTC   Qianfan Jigui 21
2026-253 → Chang Zheng 12 Y11 HCSLS/LC2 2026 Nov 8 20:24 UTC  WHDW 29
`

ill_from_gcat.py 把它转成我们的口径（**只填空字段，人工表/百科已有值不动**）：

`
2026-248 → 2026-11-03 08:15 | 力箭二号 遥二 | 酒泉 LC-140 | 千帆极轨21组
2026-253 → 2026-11-09 04:24 | 长征十二号 遥十一 | 海南商发 LC-2 | 卫星互联网低轨29组
`

管线变成 9 步：探测 → 入册 → **GCAT 补全** → 补末点 → 补缺口 → 千帆图 → 星网图 → 校验 → 烘页面。
实测：56 行被 GCAT 标注；只存在于自动表的 2026-253 也拿到了完整字段。

**因此：卫星百科降级为可选增强**（本机巡检能连上时，补研制方等更细字段），
网站本身完全由 CI 自主更新，不再依赖任何一台电脑开着。

## 七、根除按批次判断这类错误（2026-11-14）

最近连着三个 bug 是同一个病根 —— **对批次做判断，而批次成员会分批到达**：

| 现象 | 根因 |
|---|---|
| 少一颗（DIGUI-240） | 入册按批次判重：批次已登记 → 整批跳过 |
| 壳层标成 86.5° | 种子数据 shell 为空，出图时默认落到 86.5° |
| 图上只有一个点 | 回填按末点最旧排队，新批次被老星挤掉配额 |

### 做法：不变量 + 硬闸 + 故障注入

新增 check_data.py，管线第 **9/10 步**，**不带 continue-on-error**（数据不自洽就不发布）：

| 检查 | 基准 | 判定 |
|---|---|---|
| A1 | 本地 | 每颗必须带 cospar |
| A3 | **CelesTrak 组接口** | 上游有、本地没有 → 硬失败（漏星） |
| A3b | 同上 | 各批次颗数少于上游 → 硬失败 |
| B' | 同上（真实倾角） | 国网壳层与倾角不符 → 硬失败 |
| C | 本地 | 单点/久未回填 → 提示 |

关键点：**基准必须是外部数据**。第一版用发射表里的 
 和按壳层反推的倾角，
既空转（自动表没有 n 字段）又循环自证（倾角由壳层算出来必然一致）——
故障注入两次都放行，等于没装闸。

### 故障注入验证（真实数据 + 真网络）

`
删除 DIGUI-240      → ✗ A3 2026-253：上游 gw 有 1 颗本地没有（NORAD 101328）
改一颗壳层为 86.5°  → ✗ B' 国网：1 颗壳层与上游倾角不符（DIGUI-232 50.0° vs 86.5°）
恢复真实数据        → 通过：0 失败 0 提示
`

以后任何人（包括我）再引入同类错误，CI 会直接红在 9/10 步，不会发到线上。
